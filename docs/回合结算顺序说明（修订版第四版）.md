# 回合结算顺序说明（修订版第四版）

本文档用于固定原型 Demo 的回合结算流程，并补充中后期“搜打撤”框架设想。

目标：
- 把回合执行顺序写死，后续代码实现严格按此文档进行
- 提前暴露模糊规则，避免编码后反复返工
- 为后续 `ActionIntent / GameState / TurnResolver` 的数据结构设计提供依据
- 区分“第一版原型必须实现”和“后续扩展框架”

---

## 一、当前固定规则摘要

### 1. 地图与坐标
- 地图尺寸为 `7x7`
- 玩家视野为 `6x6`
- 对玩家显示的坐标系：左下角为 `(1,1)`
- 代码内部坐标系：允许继续使用左上角原点、从 `0` 开始计数
- 结论：显示坐标与内部坐标分离

### 2. 基础动作
- 每个单位每回合提交一个 `intent`
- 当前支持四类动作：
  - `MOVE`：移动到相邻 8 方向之一
  - `STAY`：原地待机
  - `PICK`：捡起当前格中的一个指定钱袋
  - `THROW`：向周围 8 方向的 1 格或 2 格目标格扔钱袋

### 3. 扔钱规则
- 扔钱数量 = 当前持有金币数除以 `2` 后向上取整
- 若当前仅有 `1` 金币，则不能执行 `THROW`
- 当玩家尝试 `THROW` 且金币不足时，此回合视为 `STAY`

### 4. 多钱袋同格
- 同一格可存在多个钱袋
- `PICK` 必须指定具体钱袋
- 表现层设想：钱袋在单元格左下角横向排开

### 5. 被砸回原格
- 投掷钱袋不会把目标格上所有单位都直接砸回
- 先进行一次“冲突判定1”，只保留目标格上的存活者
- 之后若该格被投掷钱袋命中，则只把“冲突判定1后存活的那一个单位”砸回 `prev_pos`
- 被砸回的单位，会立即失去其原目标格中的存活资格
- 若多个投掷钱袋同时命中同一格，“砸回”效果只触发一次
- 若多个单位同时被砸回同一个原格，则它们全部回原格，再在该原格进行“冲突判定2”
- 被砸回后若最终存活，则下一回合在该格强制执行 `STAY`

### 6. 普通传送门 `portal` 规则
- 普通 `portal` 为双向门，一对门有两个入口
- 单位本回合移动到有 `portal` 的格子时，本回合仍留在该格参与正常结算
- 下一回合开始时，该单位先执行传送
- 传送视为“进入目标格”
- 传送后的 `prev_pos` 记录传送前位置，也就是传送门所在单元格
- 传送来的单位不与本回合选择 `MOVE` 离开的单位判定
- 传送来的单位只与“本回合待机在该格”或“本回合移动进入该格”的单位一起进入“冲突判定1”
- 普通 `portal` 为开局固定生成，不会消失，也不会刷新更多
- 玩家乘坐过的普通 `portal` 需要在 UI 中记录入口信息
- 传送门一对两个入口都应被记录
- 只有玩家实际乘坐过，才在 UI 中记录显示

### 7. 普通传送门过热规则
- 当玩家成功使用一次普通 `portal` 后，该传送门对进入过热状态
- 这里的“该传送门对”指这对双向门的两个入口整体
- 一旦过热，该对传送门两个入口都不可传送
- 过热持续 `3` 回合
- 过热期间，这两个入口所在单元格都视为普通单元格
- `3` 回合后冷却结束，恢复可传送状态
- 若单位在过热门上停留，因其本回合被视为普通格，不会产生传送预约

### 8. `exit_portal` 规则
- `exit_portal` 与 `portal` 是两种不同对象
- 站上 `exit_portal` 的当回合不会立刻胜利
- 必须在下一回合撤离成功，才算胜利
- 撤离不会被打断，和传送一样是强制执行的系统动作
- `exit_portal` 为单人撤离门
- 若同一回合多个单位进入 `exit_portal` 所在格，则先进行冲突判定，只有存活者可在下一回合撤离
- 执行了撤离的 `exit_portal` 会消失，并刷新在另一个可落脚单元格
- 某个玩家撤离成功后，该玩家获胜并离场；若仍有其他玩家存活，则游戏继续
- 后期表现设计中，建议通过颜色区分 `portal` 与 `exit_portal`

### 9. 同格存活规则
- 一个格子在一个回合结算完成后，最多只能有一个单位存活
- 如果格内存在“纯 `STAY` 单位”，且它本回合没有执行 `PICK/THROW`，则它拥有待机占格优先权
- 若格内单位执行了 `PICK` 或 `THROW`，则不再享有待机优先权，而是进入金币比较流程
- 金币比较规则：
  1. 比较动作执行后的当前持币数，金币更少者存活
  2. 若当前持币相同，比较入场带入金币数 `entry_coins`，更少者存活
  3. 若仍相同，则随机决定

### 10. 交换位置
- 两个单位同时 `A -> B`、`B -> A` 时，互换成功
- 不视为途中相撞

### 11. 死亡掉落
- 单位死亡后，在其死亡格掉落一个钱袋
- 钱袋金额按“动作执行后的剩余持币”计算

### 12. 初始钱袋生成
- 地图初始生成钱袋时默认不叠袋
- 同格多钱袋只允许通过后续“死亡掉落”或“投掷生成”产生

### 13. 当前原型目标
- 当前 Demo 目标是规则验证沙盒
- 第一版原型优先做固定测试关卡，不急着做随机生成
- 后续正式胜利条件：随着回合数推进刷新可撤离门，成功撤离则获胜并离场，直到最后一名玩家撤离或死亡

## 二、回合总流程

一个完整游戏循环分为两层：

1. 下一回合开始阶段的系统处理
2. 本回合输入与结算

建议后续代码按以下阶段组织：

| 阶段编号 | 阶段名称 | 说明 |
| --- | --- | --- |
| 0 | 下一回合开始前处理 | 处理上一回合留下的 `portal` 传送、`exit_portal` 撤离、`portal` 冷却计数 |
| 1 | 输入阶段 | 所有单位提交本回合 `intent` |
| 2 | 动作数值预处理 | 先结算 `PICK/THROW` 对金币和钱袋的影响 |
| 3 | 理论目标格确定 | 计算所有单位本回合理论落点 |
| 4 | 环境致死预处理 | 处理风暴等环境致死格 |
| 5 | 冲突判定1 | 先判定所有正常到达目标格的单位 |
| 6 | 砸回处理 | 处理投掷钱袋导致的“只砸回冲突判定1中的存活者” |
| 7 | 冲突判定2 | 只判定所有被砸回单位所在格 |
| 8 | 死亡掉落 | 为死亡单位生成钱袋 |
| 9 | 强制待机标记 | 给被砸回且最终存活的单位打上下一回合 `forced_stay` |
| 10 | 传送预约标记 | 给本回合结束时站在可用 `portal` 上的单位记录下回合传送 |
| 11 | 撤离预约标记 | 给本回合结束时站在 `exit_portal` 上的单位记录下回合撤离 |
| 12 | 回合后地图事件 | 处理风暴扩散、撤离门刷新、终极钱袋触发等系统事件 |

## 三、标准结算顺序

以下顺序为当前版本的唯一结算顺序。

| 顺序 | 阶段 | 输入 | 输出 | 规则说明 |
| --- | --- | --- | --- | --- |
| 0 | 下一回合开始前处理 | 上一回合结束状态 | 新回合起始状态 | 先处理 `portal` 传送、`exit_portal` 撤离、传送门冷却回合减少 |
| 1 | 提交 intent | 本回合所有单位状态 | 每单位一个 `intent` | 每单位每回合只能有一个最终动作意图 |
| 2 | 结算 `PICK/THROW` 金币变化 | 单位状态、钱袋状态、intent | 更新后的单位金币、钱袋增减 | `PICK` 成功后立即移除目标钱袋；`THROW` 先扣金币再生成投掷钱袋；非法动作降级为 `STAY` |
| 3 | 确定理论目标格 | 单位状态、intent | 每单位本回合理论目标格 | `MOVE` 计算移动目标；`STAY/PICK/THROW` 理论目标格为原格；交换位置允许成功 |
| 4 | 环境致死预处理 | 理论目标格、地图环境状态 | 环境击杀结果 | 若单位位于或将进入被风暴吞噬的格，则立即死亡 |
| 5 | 冲突判定1 | 理论目标格、单位金币状态 | 每格的第一轮存活者 | 判定所有正常到达目标格的单位，包括本回合正常移动、待机、`PICK/THROW` 留在原格者，以及本回合开始时传送进入的单位 |
| 6 | 处理钱袋砸回原格 | 冲突判定1结果、投掷钱袋信息 | 被砸回单位列表、更新后的候选格 | 若某格被投掷命中，只把该格在冲突判定1后的存活者砸回 `prev_pos`；同格多投掷只触发一次砸回 |
| 7 | 冲突判定2 | 被砸回单位及其原格信息 | 被砸回单位的最终存活结果 | 只处理被砸回单位进入原格后产生的冲突 |
| 8 | 处理死亡掉落 | 死亡单位、死亡格 | 新增掉落钱袋 | 死亡单位在死亡格掉落一个金额等于其“动作执行后剩余持币”的钱袋 |
| 9 | 标记强制待机 | 被砸回且最终存活的单位 | `forced_stay_turns` 等状态 | 被砸回且最终存活者，下一回合在当前格强制 `STAY` |
| 10 | 标记传送预约 | 本回合结束状态 | `queued_teleport_to` 等状态 | 站在“可用且未过热”的 `portal` 上的单位，本回合不传送，只记录下回合开始时传送 |
| 11 | 标记撤离预约 | 本回合结束状态 | `queued_exit` 等状态 | 站在 `exit_portal` 上的单位，本回合不立刻胜利，只记录下回合撤离 |
| 12 | 回合后地图事件 | 当前回合最终状态 | 更新后的地图状态 | 处理风暴扩散、撤离门刷新、终极钱袋触发等系统事件 |

## 四、详细阶段定义

## 4.1 阶段 0：下一回合开始前处理

### 处理内容
- `portal` 传送
- `exit_portal` 撤离
- `portal` 过热冷却计数

### `portal` 传送规则
- 所有拥有传送预约的单位，在新回合开始时先被放到其 `queued_teleport_to`
- 传送后的 `prev_pos` 记录传送前位置，也就是传送门所在格
- 该移动不在“回合开始瞬间”立即单独结算冲突
- 传送后的单位将在本回合的“冲突判定1”中参与判定
- 一旦成功完成传送，该传送门对进入过热状态
- 过热影响的是这一对双向门的两个入口，而不是单个入口

### `portal` 冷却规则
- 过热持续 `3` 回合
- 可用实现方式：在传送门对上记录 `cooldown_turns`
- 每个新回合开始前，若该值大于 `0`，则减 `1`
- 当 `cooldown_turns > 0` 时，这对门两个入口都视为普通格
- 当 `cooldown_turns == 0` 时，恢复为可传送状态

### `exit_portal` 撤离规则
- 所有拥有撤离预约的单位，在新回合开始时强制执行撤离
- 撤离不会被打断
- 若撤离成功，则该单位直接脱离地图并记为胜利
- 对应的 `exit_portal` 消失，并刷新在另一个可落脚单元格
- 因此 `exit_portal` 的胜利条件是“下一回合撤离成功”，不是“站上即胜”

### 特别说明
- 传送来的单位不与“本回合选择 `MOVE` 离开的单位”判定
- 传送来的单位只会与以下单位一起在“冲突判定1”中比较：
  - 本回合待机在该格的单位
  - 本回合移动进入该格的单位
  - 本回合 `PICK/THROW` 且停留在该格的单位

---

## 4.2 阶段 1：提交 intent

### 输入
- 所有存活单位的当前状态
- 玩家输入
- NPC/敌人的决策结果

### 输出
- 每个单位一个本回合最终 `intent`

### 约束
- 每个单位每回合只允许一个最终动作
- 被标记为“下一回合强制待机”的单位，本回合无论收到什么输入，最终 `intent` 都强制改为 `STAY`
- 非法输入统一降级：
  - 非法移动 -> `STAY`
  - 金币不足导致无法 `THROW` -> `STAY`
  - 非法 `PICK` -> `STAY`

---

## 4.3 阶段 2：先结算 `PICK/THROW` 对金币数的影响

这一步只处理“金币数值变化”和“钱袋状态变化”，还不处理存活。

### `PICK`
- 仅可拾取当前格的一个指定钱袋
- 若成功：
  - 单位金币增加
  - 被拾取钱袋立即从地图移除
- 若失败：
  - 该动作视为 `STAY`

### `THROW`
- 目标必须是 8 方向 1 格或 2 格内的合法格
- 扔钱数量 = `ceil(current_coins / 2.0)`
- 若 `current_coins <= 1`，则无法 `THROW`，视为 `STAY`
- 若成功：
  - 单位金币先减少
  - 在目标格生成一个投掷钱袋
- 该投掷钱袋既是地图上的钱袋，也是本回合“砸回处理”的触发源

### 本阶段结论
- 从这一阶段开始，后续所有存活判定都基于“动作执行后的当前持币”

---

## 4.4 阶段 3：确定本回合理论目标格

### `MOVE`
- 目标格为所选相邻格

### `STAY`
- 目标格为当前格

### `PICK`
- 目标格为当前格

### `THROW`
- 目标格为当前格

### 特例：交换位置
- 两单位同时互换格子时直接成功
- 不额外产生“途中碰撞”

---

## 4.5 阶段 4：环境致死预处理

### 当前用途
- 为后续风暴系统预留统一入口

### 规则
- 若某单位当前位于被风暴吞噬的格，或本回合理论目标格是被风暴吞噬的格，则该单位立即死亡
- 被风暴吞噬的格中的钱袋立即消失
- 因环境死亡的单位不进入后续冲突判定

### 说明
- 第一版原型可以暂不实现风暴
- 但建议从数据结构层面预留该阶段，避免后面再改主流程

---

## 4.6 阶段 5：冲突判定1

这是第一轮格内存活判定。

### 参与者
- 本回合 `MOVE` 到该格的单位
- 本回合 `STAY` 在该格的单位
- 本回合 `PICK/THROW` 且停留在该格的单位
- 本回合开始时通过“可用且未过热”的 `portal` 传送到该格的单位

### 不参与者
- 本回合选择 `MOVE` 离开该格的单位，不与传送来的单位发生额外判定
- 已被环境阶段击杀的单位

### 目标
- 先为每个格子选出“第一轮存活者”

### 判定顺序

#### 情况 A：格内存在“纯 `STAY` 单位”
满足以下条件才算“纯 `STAY` 单位”：
- 本回合动作是 `STAY`
- 没有执行 `PICK`
- 没有执行 `THROW`
- 不是通过特殊系统流程伪装成的其他动作

若存在纯 `STAY` 单位：
- 该单位享有待机占格优先权
- 所有移动进入该格的单位死亡

#### 情况 B：格内无纯 `STAY` 单位
则按以下顺序判定：
1. 比较动作执行后的当前持币数，金币更少者存活
2. 若相同，比较 `entry_coins`，更少者存活
3. 若仍相同，随机决定

---

## 4.7 阶段 6：处理“钱袋砸回原格”

### 触发条件
- 某个投掷钱袋命中目标格

### 规则
- 不直接砸回目标格上的所有单位
- 先查看该格在“冲突判定1”中的最终存活者
- 若该格存在存活者，则只把这个存活者砸回 `prev_pos`
- 该单位一旦被砸回，就立即失去原目标格中的存活资格
- 原目标格不再保留该单位
- 若该格没有存活者，则本次投掷不产生砸回效果

### 多投掷同格
- 若多个投掷钱袋同时命中同一格
- 砸回效果只触发一次

---

## 4.8 阶段 7：冲突判定2

这是第二轮格内存活判定。

### 参与者
- 所有被砸回的单位
- 以及它们被砸回目标格中原本就存在并仍存活的单位

### 规则
- 若多个单位同时被砸回同一个原格，则它们全部进入该格参与判定
- 冲突判定2只处理“被砸回后产生的新冲突”
- 未受砸回影响的格，不重复进行第二次判定

### 判定逻辑
- 与冲突判定1相同：
  1. 若存在纯 `STAY` 占格优先，则纯 `STAY` 单位优先存活
  2. 否则按“当前持币 -> `entry_coins` -> 随机”决定

---

## 4.9 阶段 8：死亡掉落钱袋

### 规则
- 每个死亡单位在其死亡格生成一个钱袋
- 钱袋金额 = 该单位动作执行后的剩余持币
- 若死于风暴，则其所在格的钱袋也会被风暴立即清除

---

## 4.10 阶段 9：处理“下一回合强制待机”标记

### 标记对象
- 本回合被钱袋砸回原格，且最终存活的单位

### 标记效果
- 下一回合该单位在当前格强制执行 `STAY`

---

## 4.11 阶段 10：处理传送门预约状态

### `portal`
- 若某单位在本回合结算结束后，位于“可用且未过热”的 `portal` 上，且仍存活
- 则记录其下一回合开始时需要传送到的目标格
- 若该 `portal` 当前处于过热状态，则不记录传送预约

### `exit_portal`
- 若某单位在本回合结算结束后，位于 `exit_portal` 上，且仍存活
- 则记录其下一回合开始时执行撤离

---

## 4.12 阶段 11：回合后地图事件

### 当前扩展方向
- 终极钱袋触发
- 风暴扩散
- 撤离门刷新

### 建议顺序
1. 检查终极钱袋是否被抵达
2. 检查回合数是否达到风暴启动阈值
3. 若风暴已启动，则按规则扩散
4. 若本回合有玩家完成撤离，则刷新新的 `exit_portal`

## 五、搜打撤扩展框架

本节为中后期设计方向，不要求第一版原型全部实现。

### 1. 开局生成
- 玩家生成在地图边缘
- 地图中生成钱袋
- 越靠近地图中心，钱袋生成概率越高
- 越靠近地图中心，高金币钱袋生成概率越高

### 2. 终极钱袋
- 开局确定一个“终极钱袋”
- 终极钱袋必须是：
  - 场上开局生成的金币数最高的钱袋之一
  - 且在这些候选中最靠近地图中心的那一个

### 3. 风暴触发条件
满足以下任一条件时，开始在地图中心生成风暴：
- 有玩家到达终极钱袋所在单元格
- 或游戏进行了足够多的回合，例如 `50` 回合

### 4. 风暴扩散规则
- 风暴从地图中心开始生成
- 风暴每两回合向外扩散一圈单元格
- 若单元格被风暴吞噬：
  - 该格中的玩家立即死亡
  - 将要移动到该格的玩家立即死亡
  - 该格中的钱袋消失

### 5. 撤离门刷新
- 风暴或终极阶段开始后，在地图上随机生成 `exit_portal`
- `exit_portal` 必须刷新在可落脚单元格
- 玩家撤离成功后，该门消失，并刷新在另一个可落脚单元格

### 6. 终局
- 玩家撤离成功则该玩家获胜并离场
- 游戏继续，直到最后一个场上玩家撤离或死亡

### 7. 对当前回合框架的影响
这套扩展机制不会推翻当前结算框架，只会新增：
- 环境致死阶段
- 回合后地图事件阶段
- 若干地图状态字段

## 六、优先级总表

为避免后续实现时规则冲突，统一采用下表。

| 优先级 | 规则 |
| --- | --- |
| 1 | 下一回合开始时，先处理上一回合预约的 `portal` 传送和 `exit_portal` 撤离 |
| 2 | 下一回合开始时，处理 `portal` 冷却回合数递减 |
| 3 | 强制待机单位的输入覆盖普通输入 |
| 4 | `PICK/THROW` 的金币变化先于任何冲突判定 |
| 5 | 环境致死先于格内冲突判定 |
| 6 | 先做“冲突判定1”，再做“砸回处理”，最后只对受影响格做“冲突判定2” |
| 7 | `THROW` 命中某格时，只砸回该格在“冲突判定1”中的存活者 |
| 8 | 被砸回单位会立即失去原目标格中的存活资格 |
| 9 | 多个投掷钱袋同时命中同一格时，砸回效果只触发一次 |
| 10 | 若多个单位同时被砸回同一原格，则全部进入该格参与“冲突判定2” |
| 11 | 纯 `STAY` 的占格优先权高于普通移动进入 |
| 12 | `PICK/THROW` 不享有待机优先权，按金币比较 |
| 13 | 同格无待机优先权时，按“当前持币 -> `entry_coins` -> 随机”判定 |
| 14 | 死亡掉落发生在所有冲突判定之后 |
| 15 | 站上 `portal` 后，本回合先留在原格参与结算，下回合才传送 |
| 16 | 站上过热 `portal` 时，该格只按普通格处理 |
| 17 | 使用一次 `portal` 后，该双向门对整体过热 3 回合 |
| 18 | 站上 `exit_portal` 后，本回合不立刻胜利，下一回合撤离成功才胜利 |
| 19 | 传送后的 `prev_pos` 记录传送前所在的传送门格 |
| 20 | 撤离不会被打断 |

## 七、建议使用的数据结构字段

本节不是代码实现，只是为后续数据结构设计预留字段。

### 结论
- 你需要单独加“传送门数据结构”或至少加“传送门对数据结构”
- 不建议只把过热参数塞进单个 `TileState`
- 原因：过热作用于“一对双向门”的两个入口整体，不是某一个单元格独立状态

### 推荐做法
- `TileState` 只保存“这个格上有什么”以及它关联哪个门对
- 新增 `PortalState` 或 `PortalPairState`，专门管理：
  - 两个入口坐标
  - 当前是否过热
  - 剩余冷却回合
  - 是否已被玩家发现
  - UI 颜色标识

### UnitState
| 字段 | 含义 |
| --- | --- |
| `id` | 单位唯一标识 |
| `pos` | 当前格坐标 |
| `prev_pos` | 上一回合所在格，用于砸回；若本回合开始先传送，则记录传送前的门格 |
| `coins` | 当前持币 |
| `entry_coins` | 入场带入金币，用于同金币时比较 |
| `alive` | 是否存活 |
| `won` | 是否已撤离成功 |
| `forced_stay_turns` | 剩余强制待机回合数 |
| `queued_teleport_to` | 下一回合开始时的预约传送目标 |
| `queued_exit` | 下一回合开始时是否执行撤离 |
| `teleported_this_turn` | 本回合开始时是否刚通过 `portal` 传送，用于调试与判定追踪 |
| `discovered_portal_ids` | 该玩家已经乘坐并记录过的传送门对 ID 列表 |

### ActionIntent

## 九、当前判断

这次新增的“传送门过热”不会推翻现有回合框架，但会明确推动你把“普通传送门”从单纯格子属性提升为“一对门的独立状态对象”。

结论：
- 最好新增 `PortalPairState`，不要只靠 `TileState`
- `TileState` 负责标记格子属于哪个门对
- `PortalPairState` 负责双入口、过热、冷却、颜色、发现记录
- 当前框架仍然稳定，可以继续进入正式数据结构设计
