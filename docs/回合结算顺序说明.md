# 回合结算顺序说明

本文档用于固定原型 Demo 的回合结算流程。

目标：
- 把回合执行顺序写死，后续代码实现严格按此文档进行
- 提前暴露模糊规则，避免编码后反复返工
- 为后续 `ActionIntent / GameState / TurnResolver` 的数据结构设计提供依据

---

## 一、当前固定规则摘要

### 1. 地图与坐标
- 地图尺寸为 `7x7`
- 玩家视野为 `6x6`
- 对玩家显示的坐标系：左下角为 `(1,1)`
- 代码内部坐标系：允许继续使用左上角原点、从 `0` 开始计数
- 结论：显示坐标与内部坐标分离

### 2. 基础动作
- 每个单位每回合提交一个 `intent`
- 当前支持四类动作：
  - `MOVE`：移动到相邻 8 方向之一
  - `STAY`：原地待机
  - `PICK`：捡起当前格中的一个指定钱袋
  - `THROW`：向周围 8 方向的 1 格或 2 格目标格扔钱袋

### 3. 扔钱规则
- 扔钱数量 = 当前持有金币数除以 `2` 后向上取整
- 若当前仅有 `1` 金币，则不能执行 `THROW`
- 当玩家尝试 `THROW` 且金币不足时，此回合视为 `STAY`

### 4. 多钱袋同格
- 同一格可存在多个钱袋
- `PICK` 必须指定具体钱袋
- 表现层设想：钱袋在单元格左下角横向排开

### 5. 被砸回原格
- 若钱袋落入某目标格，而该格有单位待机，或有单位本回合移动进入该格，则该单位会被砸回“上一回合所在格”
- 若该单位本回合原本就是待机，则砸回原待机格
- 被砸回原格后，若原格也有其他单位，则在原格继续参与冲突判定
- 若被砸回后存活，则下一回合在该格强制执行 `STAY`

### 6. 传送门规则
- 单位本回合移动到有传送门的格子时，本回合仍留在该格参与正常结算
- 下一回合开始时，该单位先执行传送
- 这次传送视为“移动进入目标格”
- 因此传送后的目标格也要参与同样的冲突判定规则

### 7. 同格存活规则
- 一个格子在一个回合结算完成后，最多只能有一个单位存活
- 如果格内存在“纯 `STAY` 单位”，且它本回合没有执行 `PICK/THROW`，则它拥有待机占格优先权
- 若格内单位执行了 `PICK` 或 `THROW`，则不再享有待机优先权，而是进入金币比较流程
- 金币比较规则：
  1. 比较动作执行后的当前持币数，金币更少者存活
  2. 若当前持币相同，比较入场带入金币数 `entry_coins`，更少者存活
  3. 若仍相同，则随机决定

### 8. 交换位置
- 两个单位同时 `A -> B`、`B -> A` 时，互换成功
- 不视为途中相撞

### 9. 死亡掉落
- 单位死亡后，在其死亡格掉落一个钱袋
- 钱袋金额按“动作执行后的剩余持币”计算

### 10. 当前原型目标
- 当前 Demo 目标是规则验证沙盒
- 后续正式胜利条件：随着回合数推进刷新可撤离传送门，成功撤离则胜利

## 二、回合总流程

一个完整游戏循环分为两层：

1. 本回合输入与结算
2. 下一回合开始时的传送处理

建议后续代码按以下阶段组织：

| 阶段编号 | 阶段名称 | 说明 |
| --- | --- | --- |
| 0 | 下一回合开始前处理 | 处理上一回合留下的传送预约 |
| 1 | 输入阶段 | 所有单位提交本回合 `intent` |
| 2 | 动作数值预处理 | 先结算 `PICK/THROW` 对金币的影响 |
| 3 | 目标格确定 | 计算所有单位本回合结束时理论落点 |
| 4 | 砸回处理 | 处理钱袋命中导致的“砸回原格” |
| 5 | 格内存活判定 | 按格子逐一结算冲突与存活 |
| 6 | 死亡掉落 | 为死亡单位生成钱袋 |
| 7 | 强制待机标记 | 给被砸回且存活的单位打上下一回合 `forced_stay` |
| 8 | 传送预约标记 | 给本回合停留在传送门格上的单位记录下回合传送 |
| 9 | 进入下一回合 | 新回合开始，先处理传送，再进入输入阶段 |

## 三、标准结算顺序

以下顺序为当前版本的唯一结算顺序。

| 顺序 | 阶段 | 输入 | 输出 | 规则说明 |
| --- | --- | --- | --- | --- |
| 1 | 提交 intent | 本回合所有单位状态 | 每单位一个 `intent` | 每单位每回合只能有一个最终动作意图 |
| 2 | 结算 `PICK/THROW` 金币变化 | 单位状态、钱袋状态、intent | 更新后的单位金币、钱袋增减 | `PICK` 先把指定钱袋加入单位持币；`THROW` 先扣除投掷金币并在目标格生成投掷钱袋；非法 `THROW` 视为 `STAY` |
| 3 | 确定理论目标格 | 单位状态、intent | 每单位本回合理论目标格 | `MOVE` 计算移动目标；`STAY/PICK/THROW` 默认目标格为原格；交换位置允许成功 |
| 4 | 处理钱袋砸回原格 | 理论目标格、投掷钱袋信息 | 更新后的单位最终候选格 | 若投掷目标格上有待机单位，或有单位本回合移动进入该格，则这些被命中的单位被砸回 `prev_pos` |
| 5 | 逐格处理存活 | 最终候选格、单位金币状态 | 存活/死亡结果 | 每格结算后只允许一个单位存活；纯 `STAY` 占格优先，其余按金币规则判定 |
| 6 | 处理死亡掉落 | 死亡单位、死亡格 | 新增掉落钱袋 | 死亡单位在死亡格掉落一个金额等于其“动作执行后剩余持币”的钱袋 |
| 7 | 标记强制待机 | 被砸回且存活的单位 | `forced_stay_turns` 等状态 | 被砸回且存活者，下一回合在当前格强制 `STAY` |
| 8 | 标记传送预约 | 本回合结束状态 | `queued_teleport_to` 等状态 | 站在传送门格上的单位，本回合不传送，只记录下回合开始时传送 |
| 9 | 下一回合开始先传送 | 传送预约状态 | 新回合开局位置 | 传送视为一次“移动进入目标格”，因此传送落点仍需适用移动进入规则 |

## 四、详细阶段定义

## 4.1 阶段 1：提交 intent

### 输入
- 所有存活单位的当前状态
- 玩家输入
- NPC/敌人的决策结果

### 输出
- 每个单位一个本回合最终 `intent`

### 约束
- 每个单位每回合只允许一个最终动作
- 被标记为“下一回合强制待机”的单位，本回合无论收到什么输入，最终 `intent` 都强制改为 `STAY`
- 非法输入统一降级：
  - 非法移动 -> `STAY`
  - 金币不足导致无法 `THROW` -> `STAY`
  - 非法 `PICK` -> `STAY`

---

## 4.2 阶段 2：先结算 `PICK/THROW` 对金币数的影响

这一步只处理“金币数值变化”和“钱袋状态变化”，还不处理存活。

### `PICK`
- 仅可拾取当前格的一个指定钱袋
- 若成功：
  - 单位金币增加
  - 被拾取钱袋从地图移除
- 若失败：
  - 该动作视为 `STAY`

### `THROW`
- 目标必须是 8 方向 1 格或 2 格内的合法格
- 扔钱数量 = `ceil(current_coins / 2.0)`
- 若 `current_coins <= 1`，则无法 `THROW`，视为 `STAY`
- 若成功：
  - 单位金币先减少
  - 在目标格生成一个投掷钱袋
- 该投掷钱袋既是地图上的钱袋，也是本回合“砸回处理”的触发源

### 本阶段结论
- 从这一阶段开始，后续所有存活判定都基于“动作执行后的当前持币”

---

## 4.3 阶段 3：确定本回合理论目标格

### `MOVE`
- 目标格为所选相邻格

### `STAY`
- 目标格为当前格

### `PICK`
- 目标格为当前格

### `THROW`
- 目标格为当前格

### 特例：交换位置
- 两单位同时互换格子时直接成功
- 不额外产生“途中碰撞”

---

## 4.4 阶段 4：处理“钱袋砸回原格”

### 触发条件
- 某个投掷钱袋命中目标格
- 该格中有以下任一种单位：
  - 本回合在该格纯 `STAY`
  - 本回合 `PICK/THROW` 并仍留在该格
  - 本回合 `MOVE` 进入该格

### 处理结果
- 被命中的单位改为返回其 `prev_pos`
- 若单位本回合本来就在原格待机，则回到该原格
- 被砸回后并不保证安全，仍需在原格继续参与冲突判定

### 后续影响
- 如果该单位最终存活，则下一回合强制 `STAY`

### 当前解释
- 本规则意味着：扔钱不是直接击杀，而是“改变别人本回合最终落点”，从而制造新的格内冲突

---

## 4.5 阶段 5：逐格处理存活判定

这是回合核心判定阶段。

### 目标
- 结算后每个格子最多一个单位存活

### 判定顺序

#### 情况 A：格内存在“纯 `STAY` 单位”
满足以下条件才算“纯 `STAY` 单位”：
- 本回合动作是 `STAY`
- 没有执行 `PICK`
- 没有执行 `THROW`
- 不是通过被砸回才回到该格的特殊动作伪装

若存在纯 `STAY` 单位：
- 该单位享有待机占格优先权
- 所有移动进入该格的单位死亡

说明：
- `PICK` 和 `THROW` 虽然目标格通常仍是原格，但不算待机占格优先

#### 情况 B：格内无纯 `STAY` 单位
则按以下顺序判定：
1. 比较动作执行后的当前持币数，金币更少者存活
2. 若相同，比较 `entry_coins`，更少者存活
3. 若仍相同，随机决定

### 额外说明
- 被砸回原格的单位，按其被砸回后的格子参与该格判定
- 传送不在本阶段发生，传送只在下一回合开始时处理

---

## 4.6 阶段 6：死亡掉落钱袋

### 规则
- 每个死亡单位在其死亡格生成一个钱袋
- 钱袋金额 = 该单位动作执行后的剩余持币

### 当前解释
- 掉落金额不是回合开始时持币
- 掉落金额不是 `entry_coins`
- 掉落金额按死亡时结算状态确定

---

## 4.7 阶段 7：处理“下一回合强制待机”标记

### 标记对象
- 本回合被钱袋砸回原格，且最终存活的单位

### 标记效果
- 下一回合该单位在当前格强制执行 `STAY`
- 玩家或 AI 在该回合无法覆盖这个动作

### 建议状态字段
- `forced_stay_turns = 1`

---

## 4.8 阶段 8：处理传送门预约状态

### 规则
- 若某单位在本回合结算结束后，位于传送门格上，且仍存活
- 则记录其下一回合开始时需要传送到的目标格

### 本阶段不发生的事
- 本回合不立刻传送
- 不在本回合额外跳过任何冲突判定

### 建议状态字段
- `queued_teleport_to`

---

## 4.9 阶段 9：下一回合开始时先执行传送

### 规则
- 新回合开始前，先处理所有拥有传送预约的单位
- 传送视为“移动进入目标格”

### 含义
- 传送到目标格后，如果目标格还有其他单位，也必须进入正常冲突逻辑
- 因此传送本质上不是“无敌位移”，而是一种特殊的回合开始移动

### 实现建议
- 可以把传送作为“回合 0 阶段”的系统动作处理
- 传送完成后，再进入正常输入阶段

## 五、优先级总表

为避免后续实现时规则冲突，统一采用下表。

| 优先级 | 规则 |
| --- | --- |
| 1 | 下一回合开始时，先处理上一回合预约的传送 |
| 2 | 强制待机单位的输入覆盖普通输入 |
| 3 | `PICK/THROW` 的金币变化先于格内存活判定 |
| 4 | `THROW` 造成的砸回先于格内存活判定 |
| 5 | 纯 `STAY` 的占格优先权高于普通移动进入 |
| 6 | `PICK/THROW` 不享有待机优先权，按金币比较 |
| 7 | 同格无待机优先权时，按“当前持币 -> entry_coins -> 随机”判定 |
| 8 | 死亡掉落发生在存活判定之后 |
| 9 | 站上传送门后，本回合先留在原格参与结算，下回合才传送 |

## 六、建议使用的数据结构字段

本节不是代码实现，只是为后续数据结构设计预留字段。

### UnitState
| 字段 | 含义 |
| --- | --- |
| `id` | 单位唯一标识 |
| `pos` | 当前格坐标 |
| `prev_pos` | 上一回合所在格，用于砸回 |
| `coins` | 当前持币 |
| `entry_coins` | 入场带入金币，用于同金币时比较 |
| `alive` | 是否存活 |
| `forced_stay_turns` | 剩余强制待机回合数 |
| `queued_teleport_to` | 下一回合开始时的预约传送目标 |

### ActionIntent
| 字段 | 含义 |
| --- | --- |
| `actor_id` | 执行动作的单位 ID |
| `type` | `MOVE / STAY / PICK / THROW` |
| `target_pos` | 移动或投掷目标格 |
| `target_bag_id` | `PICK` 的目标钱袋 |
| `throw_amount` | 本回合扔出的金币数量 |

### BagState
| 字段 | 含义 |
| --- | --- |
| `id` | 钱袋唯一标识 |
| `pos` | 所在格坐标 |
| `coins` | 钱袋金币数 |
| `is_throw_bag` | 是否为本回合投掷生成的钱袋 |

## 七、当前仍需确认的问题

以下问题如果不尽快确认，后面编码仍可能返工。

### 1. 一个投掷钱袋命中目标格时，是否会把“该格所有单位”全部砸回？
当前文意更像是：
- 只要在目标格上的单位满足命中条件，就都会被砸回

请确认是否采用：
- “同一目标格中所有命中的单位全部被砸回”

### 2. 若多个单位同时被砸回同一个原格，是否全部进入该原格做冲突判定？
当前文意是“是”。
建议明确写死为：
- 是，全部回原格，再在原格做常规存活判定

### 3. 若一个单位本回合先 `PICK`，而钱袋同时又被其他规则影响，是否存在冲突？
当前最稳妥做法：
- `PICK` 在阶段 2 先完成
- 只要成功拾取，该钱袋立即从地图移除，不再参与其他逻辑

### 4. 若多个投掷钱袋同时落入同一格，是否叠加效果？
当前文档未明确。
可选方案：
- A：只要命中一次就砸回，不叠加
- B：多个钱袋都命中，但“砸回”效果只发生一次

建议采用 B，因为更容易实现，也更符合“位置控制”而不是“连锁击晕”的方向。

### 5. 传送到目标格后，是否在“新回合开始阶段”立刻做冲突判定？
当前文意是“会”，因为传送视为移动进入目标格。
建议明确写死为：
- 传送处理完成后，若目标格已有其他单位，则立刻按移动进入规则进行冲突判定，再进入输入阶段

### 6. 地图上初始生成金币袋时，是否允许多个钱袋同格？
你已经允许“同格多钱袋”，但还没明确地图生成是否允许初始就叠在一起。
建议原型第一版先定为：
- 初始生成默认不叠袋
- 后续仅通过死亡掉落或投掷产生同格多袋

### 7. 胜利传送门与普通传送门是否是同一种对象？
你现在描述中“传送门”兼有：
- 地图移动传送
- 终局撤离胜利

建议尽快分开命名：
- `portal`：地图传送门
- `exit_portal`：撤离门

否则后面状态机会混乱。

## 八、建议你现在立刻确认的最小清单

如果你想尽量避免返工，建议你接下来只确认下面 5 条：

1. 投掷命中同一格时，是否该格所有命中单位全部砸回
2. 多个投掷钱袋落在同一格时，砸回效果是否只触发一次
3. 传送到目标格后，是否在新回合开始前立刻结算冲突
4. 初始地图生成的钱袋是否允许同格叠加
5. 普通传送门与撤离门是否拆成两种对象

这些一旦定下来，后续就可以开始安全设计 `GameState` 和 `TurnResolver`。
