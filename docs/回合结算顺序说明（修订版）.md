# 回合结算顺序说明（修订版）

本文档用于固定原型 Demo 的回合结算流程。

目标：
- 把回合执行顺序写死，后续代码实现严格按此文档进行
- 提前暴露模糊规则，避免编码后反复返工
- 为后续 `ActionIntent / GameState / TurnResolver` 的数据结构设计提供依据

---

## 一、当前固定规则摘要

### 1. 地图与坐标
- 地图尺寸为 `7x7`
- 玩家视野为 `6x6`
- 对玩家显示的坐标系：左下角为 `(1,1)`
- 代码内部坐标系：允许继续使用左上角原点、从 `0` 开始计数
- 结论：显示坐标与内部坐标分离

### 2. 基础动作
- 每个单位每回合提交一个 `intent`
- 当前支持四类动作：
  - `MOVE`：移动到相邻 8 方向之一
  - `STAY`：原地待机
  - `PICK`：捡起当前格中的一个指定钱袋
  - `THROW`：向周围 8 方向的 1 格或 2 格目标格扔钱袋

### 3. 扔钱规则
- 扔钱数量 = 当前持有金币数除以 `2` 后向上取整
- 若当前仅有 `1` 金币，则不能执行 `THROW`
- 当玩家尝试 `THROW` 且金币不足时，此回合视为 `STAY`

### 4. 多钱袋同格
- 同一格可存在多个钱袋
- `PICK` 必须指定具体钱袋
- 表现层设想：钱袋在单元格左下角横向排开

### 5. 被砸回原格
- 投掷钱袋不会把目标格上所有单位都直接砸回
- 先进行一次“冲突判定1”，只保留目标格上的存活者
- 之后若该格被投掷钱袋命中，则只把“冲突判定1后存活的那一个单位”砸回 `prev_pos`
- 若多个投掷钱袋同时命中同一格，“砸回”效果只触发一次
- 若多个单位同时被砸回同一个原格，则它们全部回原格，再在该原格进行“冲突判定2”
- 被砸回后若最终存活，则下一回合在该格强制执行 `STAY`

### 6. 传送门规则
- 单位本回合移动到有 `portal` 的格子时，本回合仍留在该格参与正常结算
- 下一回合开始时，该单位先执行传送
- 传送视为“进入目标格”
- 但传送来的单位不与本回合选择 `MOVE` 离开的单位判定
- 传送来的单位只与“本回合待机在该格”或“本回合移动进入该格”的单位一起进入“冲突判定1”

### 7. 同格存活规则
- 一个格子在一个回合结算完成后，最多只能有一个单位存活
- 如果格内存在“纯 `STAY` 单位”，且它本回合没有执行 `PICK/THROW`，则它拥有待机占格优先权
- 若格内单位执行了 `PICK` 或 `THROW`，则不再享有待机优先权，而是进入金币比较流程
- 金币比较规则：
  1. 比较动作执行后的当前持币数，金币更少者存活
  2. 若当前持币相同，比较入场带入金币数 `entry_coins`，更少者存活
  3. 若仍相同，则随机决定

### 8. 交换位置
- 两个单位同时 `A -> B`、`B -> A` 时，互换成功
- 不视为途中相撞

### 9. 死亡掉落
- 单位死亡后，在其死亡格掉落一个钱袋
- 钱袋金额按“动作执行后的剩余持币”计算

### 10. 传送门类型
- `portal`：地图传送门
- `exit_portal`：撤离门
- 后期表现设计中，建议通过颜色区分不同类型的门

### 11. 初始钱袋生成
- 地图初始生成钱袋时默认不叠袋
- 同格多钱袋只允许通过后续“死亡掉落”或“投掷生成”产生

### 12. 当前原型目标
- 当前 Demo 目标是规则验证沙盒
- 后续正式胜利条件：随着回合数推进刷新可撤离传送门，成功撤离则胜利

## 二、回合总流程

一个完整游戏循环分为两层：

1. 下一回合开始阶段的传送处理
2. 本回合输入与结算

建议后续代码按以下阶段组织：

| 阶段编号 | 阶段名称 | 说明 |
| --- | --- | --- |
| 0 | 下一回合开始前处理 | 处理上一回合留下的传送预约 |
| 1 | 输入阶段 | 所有单位提交本回合 `intent` |
| 2 | 动作数值预处理 | 先结算 `PICK/THROW` 对金币和钱袋的影响 |
| 3 | 理论目标格确定 | 计算所有单位本回合理论落点 |
| 4 | 冲突判定1 | 先判定所有正常到达目标格的单位 |
| 5 | 砸回处理 | 处理投掷钱袋导致的“只砸回冲突判定1中的存活者” |
| 6 | 冲突判定2 | 只判定所有被砸回单位所在格 |
| 7 | 死亡掉落 | 为死亡单位生成钱袋 |
| 8 | 强制待机标记 | 给被砸回且最终存活的单位打上下一回合 `forced_stay` |
| 9 | 传送预约标记 | 给本回合结束时站在 `portal` 上的单位记录下回合传送 |
| 10 | 进入下一回合 | 新回合开始前先处理传送，再进入输入阶段 |

## 三、标准结算顺序

以下顺序为当前版本的唯一结算顺序。

| 顺序 | 阶段 | 输入 | 输出 | 规则说明 |
| --- | --- | --- | --- | --- |
| 1 | 提交 intent | 本回合所有单位状态 | 每单位一个 `intent` | 每单位每回合只能有一个最终动作意图 |
| 2 | 结算 `PICK/THROW` 金币变化 | 单位状态、钱袋状态、intent | 更新后的单位金币、钱袋增减 | `PICK` 成功后立即移除目标钱袋；`THROW` 先扣金币再生成投掷钱袋；非法动作降级为 `STAY` |
| 3 | 确定理论目标格 | 单位状态、intent | 每单位本回合理论目标格 | `MOVE` 计算移动目标；`STAY/PICK/THROW` 理论目标格为原格；交换位置允许成功 |
| 4 | 冲突判定1 | 理论目标格、单位金币状态 | 每格的第一轮存活者 | 判定所有正常到达目标格的单位，包括本回合正常移动、待机、`PICK/THROW` 留在原格者，以及本回合开始时传送进入的单位 |
| 5 | 处理钱袋砸回原格 | 冲突判定1结果、投掷钱袋信息 | 被砸回单位列表、更新后的候选格 | 若某格被投掷命中，只把该格在冲突判定1后的存活者砸回 `prev_pos`；同格多投掷只触发一次砸回 |
| 6 | 冲突判定2 | 被砸回单位及其原格信息 | 被砸回单位的最终存活结果 | 只处理被砸回单位进入原格后产生的冲突 |
| 7 | 处理死亡掉落 | 死亡单位、死亡格 | 新增掉落钱袋 | 死亡单位在死亡格掉落一个金额等于其“动作执行后剩余持币”的钱袋 |
| 8 | 标记强制待机 | 被砸回且最终存活的单位 | `forced_stay_turns` 等状态 | 被砸回且最终存活者，下一回合在当前格强制 `STAY` |
| 9 | 标记传送预约 | 本回合结束状态 | `queued_teleport_to` 等状态 | 站在 `portal` 上的单位，本回合不传送，只记录下回合开始时传送 |
| 10 | 下一回合开始先传送 | 传送预约状态 | 新回合开局位置 | 传送发生在下一回合开始时，并在该回合的“冲突判定1”阶段参与判定 |

## 四、详细阶段定义

## 4.1 阶段 0：下一回合开始前处理传送

### 输入
- 上一回合结束后仍存活的单位状态
- 单位的 `queued_teleport_to`

### 输出
- 新回合开始时的更新后位置

### 规则
- 所有拥有传送预约的单位，在新回合开始时先被放到其 `queued_teleport_to`
- 该移动不在“回合开始瞬间”立即单独结算冲突
- 传送后的单位将在本回合的“冲突判定1”中参与判定

### 特别说明
- 传送来的单位不与“本回合选择 `MOVE` 离开的单位”判定
- 传送来的单位只会与以下单位一起在“冲突判定1”中比较：
  - 本回合待机在该格的单位
  - 本回合移动进入该格的单位
  - 本回合 `PICK/THROW` 且停留在该格的单位

---

## 4.2 阶段 1：提交 intent

### 输入
- 所有存活单位的当前状态
- 玩家输入
- NPC/敌人的决策结果

### 输出
- 每个单位一个本回合最终 `intent`

### 约束
- 每个单位每回合只允许一个最终动作
- 被标记为“下一回合强制待机”的单位，本回合无论收到什么输入，最终 `intent` 都强制改为 `STAY`
- 非法输入统一降级：
  - 非法移动 -> `STAY`
  - 金币不足导致无法 `THROW` -> `STAY`
  - 非法 `PICK` -> `STAY`

---

## 4.3 阶段 2：先结算 `PICK/THROW` 对金币数的影响

这一步只处理“金币数值变化”和“钱袋状态变化”，还不处理存活。

### `PICK`
- 仅可拾取当前格的一个指定钱袋
- 若成功：
  - 单位金币增加
  - 被拾取钱袋立即从地图移除
- 若失败：
  - 该动作视为 `STAY`

### `THROW`
- 目标必须是 8 方向 1 格或 2 格内的合法格
- 扔钱数量 = `ceil(current_coins / 2.0)`
- 若 `current_coins <= 1`，则无法 `THROW`，视为 `STAY`
- 若成功：
  - 单位金币先减少
  - 在目标格生成一个投掷钱袋
- 该投掷钱袋既是地图上的钱袋，也是本回合“砸回处理”的触发源

### 本阶段结论
- 从这一阶段开始，后续所有存活判定都基于“动作执行后的当前持币”

---

## 4.4 阶段 3：确定本回合理论目标格

### `MOVE`
- 目标格为所选相邻格

### `STAY`
- 目标格为当前格

### `PICK`
- 目标格为当前格

### `THROW`
- 目标格为当前格

### 特例：交换位置
- 两单位同时互换格子时直接成功
- 不额外产生“途中碰撞”

---

## 4.5 阶段 4：冲突判定1

这是第一轮格内存活判定。

### 参与者
- 本回合 `MOVE` 到该格的单位
- 本回合 `STAY` 在该格的单位
- 本回合 `PICK/THROW` 且停留在该格的单位
- 本回合开始时通过 `portal` 传送到该格的单位

### 不参与者
- 本回合选择 `MOVE` 离开该格的单位，不与传送来的单位发生额外判定

### 目标
- 先为每个格子选出“第一轮存活者”

### 判定顺序

#### 情况 A：格内存在“纯 `STAY` 单位”
满足以下条件才算“纯 `STAY` 单位”：
- 本回合动作是 `STAY`
- 没有执行 `PICK`
- 没有执行 `THROW`
- 不是通过特殊系统流程伪装成的其他动作

若存在纯 `STAY` 单位：
- 该单位享有待机占格优先权
- 所有移动进入该格的单位死亡

#### 情况 B：格内无纯 `STAY` 单位
则按以下顺序判定：
1. 比较动作执行后的当前持币数，金币更少者存活
2. 若相同，比较 `entry_coins`，更少者存活
3. 若仍相同，随机决定

### 本阶段产物
- 每个格在“正常到达状态”下的唯一存活者
- 这些存活者中的一部分，后面可能还会被投掷钱袋砸回

---

## 4.6 阶段 5：处理“钱袋砸回原格”

### 触发条件
- 某个投掷钱袋命中目标格

### 规则
- 不直接砸回目标格上的所有单位
- 先查看该格在“冲突判定1”中的最终存活者
- 若该格存在存活者，则只把这个存活者砸回 `prev_pos`
- 若该格没有存活者，则本次投掷不产生砸回效果

### 多投掷同格
- 若多个投掷钱袋同时命中同一格
- 砸回效果只触发一次

### 结果
- 被砸回单位离开其在冲突判定1中存活的格
- 被砸回到 `prev_pos`
- 被砸回后并不保证安全，仍需在原格参加“冲突判定2”

### 当前解释
- `THROW` 不是直接杀伤
- `THROW` 是先允许目标格产生一个第一轮存活者，再把这个存活者强制改位，从而制造第二轮冲突

---

## 4.7 阶段 6：冲突判定2

这是第二轮格内存活判定。

### 参与者
- 所有被砸回的单位
- 以及它们被砸回目标格中原本就存在并仍存活的单位

### 规则
- 若多个单位同时被砸回同一个原格，则它们全部进入该格参与判定
- 冲突判定2只处理“被砸回后产生的新冲突”
- 未受砸回影响的格，不重复进行第二次判定

### 判定逻辑
- 与冲突判定1相同：
  1. 若存在纯 `STAY` 占格优先，则纯 `STAY` 单位优先存活
  2. 否则按“当前持币 -> `entry_coins` -> 随机”决定

### 结果
- 每个被砸回涉及的格，最终也只保留一个存活者

---

## 4.8 阶段 7：死亡掉落钱袋

### 规则
- 每个死亡单位在其死亡格生成一个钱袋
- 钱袋金额 = 该单位动作执行后的剩余持币

### 当前解释
- 掉落金额不是回合开始时持币
- 掉落金额不是 `entry_coins`
- 掉落金额按死亡时结算状态确定

---

## 4.9 阶段 8：处理“下一回合强制待机”标记

### 标记对象
- 本回合被钱袋砸回原格，且最终存活的单位

### 标记效果
- 下一回合该单位在当前格强制执行 `STAY`
- 玩家或 AI 在该回合无法覆盖这个动作

### 建议状态字段
- `forced_stay_turns = 1`

---

## 4.10 阶段 9：处理传送门预约状态

### 规则
- 若某单位在本回合结算结束后，位于 `portal` 上，且仍存活
- 则记录其下一回合开始时需要传送到的目标格

### 本阶段不发生的事
- 本回合不立刻传送
- 不在本回合额外跳过任何冲突判定

### 建议状态字段
- `queued_teleport_to`

---

## 五、优先级总表

为避免后续实现时规则冲突，统一采用下表。

| 优先级 | 规则 |
| --- | --- |
| 1 | 下一回合开始时，先处理上一回合预约的 `portal` 传送 |
| 2 | 强制待机单位的输入覆盖普通输入 |
| 3 | `PICK/THROW` 的金币变化先于任何冲突判定 |
| 4 | 先做“冲突判定1”，再做“砸回处理”，最后只对受影响格做“冲突判定2” |
| 5 | `THROW` 命中某格时，只砸回该格在“冲突判定1”中的存活者 |
| 6 | 多个投掷钱袋同时命中同一格时，砸回效果只触发一次 |
| 7 | 若多个单位同时被砸回同一原格，则全部进入该格参与“冲突判定2” |
| 8 | 纯 `STAY` 的占格优先权高于普通移动进入 |
| 9 | `PICK/THROW` 不享有待机优先权，按金币比较 |
| 10 | 同格无待机优先权时，按“当前持币 -> `entry_coins` -> 随机”判定 |
| 11 | 死亡掉落发生在所有冲突判定之后 |
| 12 | 站上 `portal` 后，本回合先留在原格参与结算，下回合才传送 |
| 13 | 传送来的单位在本回合“冲突判定1”中参与判定，不提前单独结算 |
| 14 | `portal` 与 `exit_portal` 是两种不同对象，后期表现层应用颜色区分 |

## 六、建议使用的数据结构字段

本节不是代码实现，只是为后续数据结构设计预留字段。

### UnitState
| 字段 | 含义 |
| --- | --- |
| `id` | 单位唯一标识 |
| `pos` | 当前格坐标 |
| `prev_pos` | 上一回合所在格，用于砸回 |
| `coins` | 当前持币 |
| `entry_coins` | 入场带入金币，用于同金币时比较 |
| `alive` | 是否存活 |
| `forced_stay_turns` | 剩余强制待机回合数 |
| `queued_teleport_to` | 下一回合开始时的预约传送目标 |
| `teleported_this_turn` | 本回合开始时是否刚通过 `portal` 传送，用于调试与判定追踪 |

### ActionIntent
| 字段 | 含义 |
| --- | --- |
| `actor_id` | 执行动作的单位 ID |
| `type` | `MOVE / STAY / PICK / THROW` |
| `target_pos` | 移动或投掷目标格 |
| `target_bag_id` | `PICK` 的目标钱袋 |
| `throw_amount` | 本回合扔出的金币数量 |

### BagState
| 字段 | 含义 |
| --- | --- |
| `id` | 钱袋唯一标识 |
| `pos` | 所在格坐标 |
| `coins` | 钱袋金币数 |
| `is_throw_bag` | 是否为本回合投掷生成的钱袋 |

### TileState
| 字段 | 含义 |
| --- | --- |
| `pos` | 格坐标 |
| `tile_type` | 普通格 / `portal` / `exit_portal` |
| `portal_target` | 若为 `portal`，则记录传送目标格 |
| `portal_color_id` | 后期表现层可用的颜色标识 |

## 七、当前仍建议补充确认的问题

你已经把最关键的返工点基本定下来了。下面这些不是阻塞项，但建议尽快补全。

### 1. 冲突判定1后被砸回的单位，原先在目标格“赢下来的存活资格”是否完全失效？
当前文档默认答案是：
- 是
- 一旦被砸回，就离开原目标格
- 原目标格不再保留该单位

### 2. 若某格在冲突判定1后无存活者，而该格同时被投掷命中，是否直接忽略砸回？
当前文档默认答案是：
- 是
- 因为没有“可被砸回的存活者”

### 3. 传送后的 `prev_pos` 应记录哪里？
建议明确为：
- 传送发生前所在格

这样后续如果传送来的单位又被 `THROW` 砸回，规则会更一致。

### 4. `exit_portal` 的胜利判定是在“站上该格立刻胜利”，还是“像普通 portal 一样下一回合撤离”？
你现在只明确了它与 `portal` 分开命名，但胜利触发时机还没完全写死。

### 5. 中心低金币概率的地图生成规则是否要在第一版原型中落地？
建议第一版先做成固定测试关卡，不急着上随机生成。

---

## 八、建议你现在立刻确认的最小清单

如果你想尽量避免返工，建议你接下来只再确认下面 3 条：

1. 被砸回的单位，其原目标格中的“存活资格”是否立即失效
2. 传送后的 `prev_pos` 记录传送前位置，是否确认
3. `exit_portal` 的胜利触发时机到底是“站上即胜”还是“下一回合撤离成功才胜”

这 3 条一旦定下来，后续就可以开始安全设计 `GameState` 和 `TurnResolver`。
